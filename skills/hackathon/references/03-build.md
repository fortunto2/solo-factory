# 03 · Build

- **When:** hacking hours, after `docs/event.md` exists.
- **Inputs:** `docs/event.md` (required stack, judging, submission fields), the chosen product.
- **Output files:** the project itself; `docs/submission.md` (the checklist below, ticked).

Planning and coding are other skills: `/plan` for the task list, `/build` to execute it, `/deploy`
for a live link. This stage only adds what a hackathon changes.

## Before the first line

- **Required stack, by exact name.** Each "must use" from `event.md` maps to a file or a call in
  the demo. A required tool you do not use costs a criterion; a tool you claim and do not use
  costs the room.
- **Pre-built vs built today.** Write the split into the README now. Most rules allow earlier
  open-source work if it is disclosed; the README says which is which.
- **Demo first.** Decide the one thing the judges will see working, and build backwards from it.
  Simple and working on the day beats elaborate and working on Monday.

## Lock the story the night before

A concept added on the last morning takes over the Q&A and the running software never comes up.
Freeze the problem, the payer and the demo path; after that only fix what breaks the demo.

## Submission checklist (`docs/submission.md`)

- [ ] repo public (if required), README: what it does, how to run it, pre-built vs built today,
      what is not validated
- [ ] live link or a recorded demo that does not depend on venue Wi-Fi
- [ ] video within the length limit from `event.md`; first 10 seconds show the product
- [ ] tracks and sponsor prizes chosen; each one's requirement visibly met
- [ ] platform fields filled (tagline length, Built With, team members added)
- [ ] submitted before the deadline in the event's time zone, with 30 minutes to spare
